# 보안·데이터·컴플라이언스 설계 — 멀티테넌트 SaaS 전환

> 관점: 보안/데이터 아키텍트. 현재 앱은 인증·서버·테넌트 개념이 전무한 **단일 사용자 localStorage 도구**이므로, 아래 항목의 대부분은 "신규 구축"이며 기존 코드에 대한 보완이 아니다. 각 항목은 체크리스트로 정리하되, 근거가 되는 코드 위치를 함께 표기한다.

## 0. 보안 관점 현재 상태 진단 (코드 근거)

전환 전 반드시 인지해야 할 구조적 노출 지점.

- [ ] **테넌트/신원 부재**: 전 엔티티에 `tenantId` 없음(`types/index.ts:1-45`), 사용자 식별이 문자열 위조 `createdBy: 'current-user'`(`hooks/useDataStore.ts:169`), `reviewerId: '1'`(`ProjectReview.tsx:114`). → 격리·인가의 토대가 없음.
- [ ] **민감정보 평문 클라이언트 저장**: 개인정보(`email`)·요율(`hourlyRate`, 인사/원가 민감정보)이 `types/index.ts:6,8`에 정의되어 있고, localStorage에 **평문 JSON**으로 저장(`useDataStore.ts:22,32`). 브라우저·XSS·공유 PC에서 그대로 노출.
- [ ] **무통제 데이터 반출입**: `exportData`가 전체 데이터를 JSON 파일로 다운로드(`useDataStore.ts:298`), `importData(data: any)`는 스키마 검증 없이 상태를 통째로 대체(`:316`). 감사·권한·검증이 전혀 없는 egress/ingress 경로.
- [ ] **전역 단일 저장 네임스페이스**: `STORAGE_KEYS = pm_members/pm_projects/...`(`useDataStore.ts:12`) — 테넌트 구분 없음.
- [ ] **접근제어·감사로그·전송보안 전무**: 백엔드가 없어 TLS·인증·권한검사·감사추적 개념 자체가 부재.

## 1. 테넌트 데이터 격리 · 유출 방지 · 권한 경계

### 1-1. 격리 모델 · 쿼리 레벨 tenant 강제
- [ ] **격리 전략 결정**: `단일 DB + Row-Level Security(RLS)` / `스키마 분리` / `DB 분리` 중 택1. 인력·요율·원가라는 **금액 민감도**를 고려하면 최소 RLS, 대형/규제 고객 대상이면 스키마 분리를 옵션으로. (미해결 — PO/사용자 결정 필요)
- [ ] **전 도메인 엔티티에 `tenantId` 필수 컬럼** 추가: `Member`, `Project`, `ProjectAllocation`, `MemberManmonth`, `ReviewComment` 및 향후 마스터(그룹·근무캘린더·요율정책). NULL 불가 + 인덱스.
- [ ] **PostgreSQL RLS 정책 강제**: 모든 테이블에 `USING (tenant_id = current_setting('app.tenant_id'))` 정책. 세션 시작 시 인증 미들웨어가 `app.tenant_id`를 주입, 애플리케이션 코드가 실수로 WHERE를 빠뜨려도 **DB가 최종 방어선**이 되게 함.
- [ ] **애플리케이션 레벨 tenant 강제(방어 심층화)**: ORM/쿼리 레이어에 tenant-scoped repository를 두어 raw 쿼리 금지. 크로스 테넌트 조회는 별도 명시적 권한(플랫폼 관리자)만 허용.
- [ ] **테넌트 컨텍스트 검증**: 모든 API 요청에서 `요청 리소스의 tenantId == 인증 토큰의 tenantId` 재확인(IDOR 방지). URL/바디의 ID를 신뢰하지 않음.
- [ ] **테넌트 스코프 회귀 테스트**: "테넌트 A 토큰으로 테넌트 B 리소스 접근 시 403/404"를 자동 테스트로 고정. 신규 엔티티 추가 시 격리 테스트 필수(품질 게이트에 편입).
- [ ] **캐시/파생 데이터 격리**: 서버 집계 캐시(materialized/Redis) 키에 `tenantId` 포함. 클라이언트 localStorage 캐시도 `tenantId` 네임스페이스로 분리하고, 로그아웃/테넌트 전환 시 즉시 purge.

### 1-2. 권한 경계 (RBAC)
- [ ] **시스템 역할을 직무(`role`)와 분리**: 현재 `Member.role`은 "시니어 기획자" 같은 직무 문자열(`types/index.ts:4`)일 뿐 권한이 아님. `본부장/사업관리/팀리드/멤버/뷰어/플랫폼관리자` 등 **접근권한용 역할**을 별도 엔티티(`Membership: User×Tenant×Role`)로 정의.
- [ ] **액션별 권한 게이트(서버·클라이언트 양쪽)**: 프로젝트 승인(`approvedBy`), 반려, 멤버 삭제, 요율 조회/수정, 데이터 내보내기, 테넌트 설정 변경에 최소 권한 원칙 적용. 서버가 최종 판정, 클라이언트는 UI 숨김만.
- [ ] **요율·원가 필드 필드레벨 권한**: `hourlyRate`·비용·유휴비용은 재무 민감정보 → 일반 멤버 응답에서 **마스킹/제외**, 권한자에게만 노출(파생 계산의 서버화와 연동).
- [ ] **승인 워크플로우에 실 권한 결합**: `draft→review→approved` 상태전이(`Project.status`)를 지정된 리뷰어/승인자 권한과 바인딩. `reviewers`/`approvedBy`를 인증 신원에서만 주입.
- [ ] **최소 권한·권한 상승 감사**: 역할 부여/회수, 관리자 권한 사용을 감사로그에 기록.

## 2. 민감정보 처리 · 암호화 · 접근제어 · 감사로그

### 2-1. 개인정보보호법(PIPA) 대응
- [ ] **개인정보 인벤토리 작성**: 처리 항목 = 성명·이메일(`email`)·직무·소속그룹, 그리고 **요율/급여성 정보(`hourlyRate`)는 인사·원가 민감정보**로 별도 등급 관리. 처리 목적·보유기간·처리위탁 현황을 문서화.
- [ ] **처리 근거·동의**: 임직원 인력정보는 대개 계약이행/정당한 이익 근거이나, 요율/평가성 데이터는 목적 제한. 테넌트(고용주)를 **개인정보처리자**, 자사를 **수탁자**로 하는 역할 정의.
- [ ] **개인정보 처리방침·위탁계약(수탁)**: 테넌트와의 계약에 처리 목적·항목·보유기간·재위탁(서브프로세서)·안전성 확보조치 명시.
- [ ] **정보주체 권리 대응 절차**: 열람·정정·삭제·처리정지 요청 처리 흐름(테넌트 관리자 경유) 정의.
- [ ] **최소수집·목적제한**: 신규 필드 추가 시 목적 없는 개인정보 수집 금지. avatar/자유텍스트(리뷰 코멘트)에 민감정보 유입 주의.
- [ ] **국외이전 고지**: 클라우드/서브프로세서가 국외일 경우 이전 국가·항목·목적 고지 및 동의/근거 확보.
- [ ] **개인정보 안전성 확보조치 기준 준수**: 접근권한 관리·접근통제·암호화·접속기록 보관(아래 항목과 매핑).

### 2-2. 암호화 (저장/전송)
- [ ] **전송 구간(in transit)**: 전 구간 TLS 1.2+ 강제, HSTS, 안전하지 않은 리다이렉트 차단. API·정적자산·관리 콘솔 모두.
- [ ] **저장 구간(at rest)**: DB·백업·오브젝트 스토리지 암호화(디스크/TDE). 관리형 KMS로 키 관리·정기 로테이션.
- [ ] **필드 레벨 암호화(민감도 최상)**: `hourlyRate`, 급여성/평가성 데이터, 인증 비밀은 컬럼 암호화 또는 애플리케이션 레벨 암호화 검토. 검색 필요성과 트레이드오프 명시.
- [ ] **비밀정보 저장금지·비밀관리**: 토큰/키/DB자격증명을 코드·저장소·클라이언트 번들에 두지 않음(`documentation.md`·`backend.md` 규칙과 일치). Secret Manager 사용.
- [ ] **클라이언트 저장 강등**: localStorage에 원가·요율·개인정보 **평문 잔류 금지**. 캐시가 불가피하면 비민감 필드로 한정, 로그아웃 시 purge, 세션 스토리지/메모리 우선.
- [ ] **비밀번호/인증 정보**: 해시(Argon2/bcrypt) 저장, 로그인 SSO/OAuth 우선. 자체 비번 시 정책·재설정·무차별 대입 방어.

### 2-3. 접근제어
- [ ] **인증 도입**: 로그인·세션(JWT/세션쿠키)·SSO(OAuth/SAML)·이메일. 세션 만료·재발급·동시세션 관리.
- [ ] **MFA**: 관리자/본부장 등 고권한 계정 다단계 인증 필수화 옵션.
- [ ] **관리자 접근 분리**: 플랫폼 운영자 콘솔과 테넌트 사용자 앱 분리, 운영자의 테넌트 데이터 접근은 사유 기록·최소권한·시간제한(Just-in-time) 접근.
- [ ] **입력 신뢰 금지**: 서버 응답·클라이언트 입력 런타임 스키마 검증(`importData(data: any)` 패턴 폐기, `zod` 등으로 계약 검증).
- [ ] **네트워크·인프라 접근통제**: DB는 사설망·IP 허용목록, 관리 포트 비공개, 최소 권한 IAM.

### 2-4. 감사로그(Audit Log)
- [ ] **감사 이벤트 정의**: 로그인/실패, 권한 변경, 프로젝트 승인/반려, 멤버·요율 생성/수정/삭제, 데이터 내보내기/가져오기, 테넌트 설정 변경, 관리자 크로스테넌트 접근.
- [ ] **로그 필드 표준화**: `who(userId)`, `tenantId`, `action`, `target(엔티티/ID)`, `before/after 요약`, `timestamp`, `ip/agent`. — 현재 없는 `updatedAt`/변경주체 필드 도입과 연동.
- [ ] **불변·분리 보관**: 감사로그는 append-only, 애플리케이션 DB와 분리(변조·삭제 방지), 접근제어 및 보존기간(예: 1년+) 설정. PIPA "접속기록 보관·점검" 요건 충족.
- [ ] **개인정보 접속기록**: 개인정보 취급자의 열람·다운로드 기록 별도 보관·정기 점검.
- [ ] **로그 내 민감정보 마스킹**: 요율·개인정보를 로그 본문에 평문 기록 금지.

## 3. 백업/복구 · 데이터 이관/삭제(오프보딩) · 서브프로세서

### 3-1. 백업/복구
- [ ] **자동 백업**: DB 정기 백업(스냅샷 + PITR), 오브젝트 스토리지 버전관리. 백업도 암호화·테넌트 데이터 포함.
- [ ] **RPO/RTO 정의**: 목표 복구시점(예: ≤15분, PITR)·목표 복구시간(예: ≤4시간) 문서화 및 SLA와 정합.
- [ ] **복구 훈련**: 정기 복구 리허설(백업 유효성 검증), 결과 기록. "백업 있음 ≠ 복구 가능".
- [ ] **랜섬/삭제 대비**: 오프사이트/불변(immutable) 백업, 소프트 삭제 + 유예기간(휴지통) 도입.
- [ ] **정합성 있는 백업**: allocation/manmonth 파생 재계산이 서버화된 후, 스냅샷 시점의 원천-파생 정합 보장.

### 3-2. 데이터 이관·삭제 (테넌트 오프보딩)
- [ ] **데이터 이식성(export)**: 테넌트 관리자가 자사 전체 데이터를 표준 포맷(JSON/CSV)으로 내보내기 — 기존 `exportData`(`useDataStore.ts:298`)를 **테넌트 스코프 + 권한 + 감사 기록** 위에서 재구현.
- [ ] **오프보딩 절차 정의**: 계약 종료 시 (1) 접근 차단 → (2) 유예기간 내 데이터 반출 지원 → (3) 안전 삭제 → (4) 삭제 증빙 제공.
- [ ] **완전 삭제(파기) 보장**: 운영 DB·백업·캐시·로그·서브프로세서까지 삭제 대상 범위 정의. 백업 롤오프 주기 내 파기·경과 시점 명시(즉시 물리삭제가 불가한 백업은 보존주기 만료 시 파기).
- [ ] **삭제 증빙·감사**: 삭제 실행 주체·시점·범위 기록, 파기확인서 발급 프로세스.
- [ ] **파괴적 작업 이중 확인**: 테넌트 전체 삭제/초기화는 다단계 확인·권한·감사 필수(`resetToDefaultData` 패턴을 서버·권한 게이트로 격상, `backend.md`·`quality-check.md` "되돌릴 수 없는 작업" 규칙 준수).
- [ ] **개인정보 보유기간 만료 삭제**: 퇴사자/종료 프로젝트 데이터의 보유기간 정책·자동 파기.

### 3-3. 서브프로세서(수탁자) 관리
- [ ] **서브프로세서 목록 공개**: 클라우드(예: AWS/GCP), 메일, 모니터링, 에러추적, 분석 등 처리 위탁 대상·위치·목적을 문서화·공개.
- [ ] **재위탁 계약·DPA**: 각 서브프로세서와 개인정보 처리 위탁계약(안전성 확보조치·국외이전 포함). 테넌트에게 재위탁 사실 고지·변경 통지 절차.
- [ ] **서브프로세서 변경 통지**: 신규 추가/교체 시 사전 통지 기간·이의제기 절차 정의.
- [ ] **데이터 소재지 통제**: 리전 고정(예: 한국/아태) 옵션, 국외이전 최소화 및 고지.

## 4. SaaS 신뢰 요소 (가용성 · 투명성)

### 4-1. 가용성 · 안정성
- [ ] **SLA 정의·공개**: 가용성 목표(예: 99.9%), 유지보수 창(maintenance window), 크레딧 정책.
- [ ] **다중화·무중단**: 다중 AZ, 무중단 배포(블루-그린/롤링), DB failover. 단일 장애점 제거.
- [ ] **모니터링·알림**: 가용성/지연/에러율/자원 지표 관측(APM), 이상 임계 알림, 온콜 체계.
- [ ] **성능·확장성**: 파생 집계의 서버화·사전집계·캐시로 대형 테넌트(수천 멤버) 대응. Rate limiting·부하 대비.
- [ ] **장애 대응·사후분석**: 인시던트 대응 절차(등급·소통·복구), Postmortem 문서화.

### 4-2. 상태페이지 · 투명성 · 신뢰
- [ ] **상태페이지(Status Page)**: 실시간 서비스 상태·장애 이력·유지보수 공지 공개. 구독 알림 제공.
- [ ] **보안·신뢰 센터**: 보안 백서/개인정보 처리방침/서브프로세서 목록/데이터 처리 위치를 한 곳에서 공개.
- [ ] **취약점 대응**: 취약점 신고 창구(보안 연락처), 정기 취약점 점검·의존성 스캔(현 스택: Tailwind v4 beta 등 프리릴리스 의존성 점검 포함).
- [ ] **인증·컴플라이언스 로드맵**: ISMS-P(국내), 필요 시 SOC 2 / ISO 27001 로드맵 명시(엔터프라이즈 신뢰 확보).
- [ ] **변경·중단 통지 정책**: 주요 변경·데이터 영향·서비스 종료(EOL) 시 사전 통지 SLA.
- [ ] **책임 공유 모델 명시**: 테넌트(관리자 권한/사용자 관리)와 자사(인프라/플랫폼 보안)의 책임 경계 문서화.

## 6. 미해결 · 의사결정 필요 (가정 금지, PO/사용자 결정)

- 격리 방식: `단일 DB + RLS` vs `스키마/DB 분리` — 고객 규모·규제 요구에 따라.
- 데이터 소재지·서브프로세서: 국내 리전 강제 여부, 국외이전 허용 범위.
- 컴플라이언스 목표 수준: ISMS-P/SOC 2/ISO 27001 중 우선순위와 시점.
- 요율/급여성 정보 취급 정책: 필드레벨 암호화·마스킹 범위, 열람 권한 등급.
- 기존 localStorage 사용자 데이터 이관: 마이그레이션 대상 포함 여부(포함 시 이관 중 평문 데이터 취급 절차 필요).
- 보유기간·파기 정책 수치(개인정보/감사로그/백업 각각) 및 SLA 목표치.

**영향받는 핵심 파일/타입**: `types/index.ts`(전 엔티티 `tenantId`·`updatedAt`·변경주체 추가, 계약 검증), `hooks/useDataStore.ts`(저장 네임스페이스·export/import·평문 저장 경로 재설계), `data/mockData.ts`(요율·개인정보 시드 → 테넌트 실데이터/빈 상태), `components/ProjectReview.tsx`·승인 액션(신원·권한 결합), 신규 백엔드(RLS·감사로그·KMS·집계 서버화).
