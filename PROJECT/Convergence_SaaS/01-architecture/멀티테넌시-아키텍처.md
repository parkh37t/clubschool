## 1. 테넌트 격리 모델 비교·권고

### 1-1. 3가지 모델 비교

| 기준 | 공유 DB + row-level(`tenant_id`)+RLS | Schema-per-tenant | DB-per-tenant |
| --- | --- | --- | --- |
| 격리 강도 | 중(논리적, RLS로 강제) | 중상(스키마 경계) | 상(물리적 완전 격리) |
| 테넌트당 비용 | **매우 낮음**(풀링) | 낮음~중 | 높음(유휴 자원 다수) |
| 운영/마이그레이션 | **단순**(마이그레이션 1회) | 복잡(N개 스키마 fan-out) | 매우 복잡(N개 DB fan-out) |
| 블래스트 반경 | 큼(쿼리 버그 시 교차 노출 위험) → RLS로 방어 | 중 | **작음** |
| 교차테넌트 분석 | **쉬움**(벤치마킹/집계 용이) | 어려움 | 매우 어려움 |
| 백업/복구 단위 | 테넌트 단위 복구 번거로움 | 스키마 단위 가능 | **테넌트 단위 자연스러움** |
| 데이터 레지던시/규제 | 약함 | 중 | **강함** |
| Postgres 한계 | 인덱스만 잘 잡으면 수천 테넌트 OK | 스키마/테이블 수천 개 시 카탈로그 팽창·성능 저하 | 커넥션/풀링 경제성 붕괴 |
| 적합 시나리오 | **소데이터·다수 테넌트(본 제품)** | 중간 규모·테넌트별 커스터마이즈 | 소수 대형·강규제 고객 |

### 1-2. 권고: 공유 DB + RLS (하이브리드 에스케이프 해치)

**이 제품에 공유 DB가 맞는 이유:**
- 테넌트당 도메인 데이터가 작다(56명 규모가 표준). schema/DB-per-tenant는 유휴 자원과 마이그레이션 fan-out 비용만 낳는다.
- 향후 "동종 업계 평균 가동률" 같은 **교차테넌트 벤치마킹**이 제품 가치가 될 수 있는데, 공유 DB가 이를 가장 쉽게 한다.
- 운영팀이 작다 → 마이그레이션·백업·모니터링을 1개 DB로 수렴시키는 이점이 크다.

**격리는 2중으로 강제(방어적 심층):**
1. **DB 계층 — Postgres RLS**: 모든 테이블에 `tenant_id NOT NULL`, 정책 `USING (tenant_id = auth.jwt()->>'tenant_id')`. 앱 버그가 있어도 DB가 교차 조회를 차단.
2. **앱 계층 — 리포지토리에서 항상 `tenant_id` 필터**. 클라이언트는 **`tenant_id`를 절대 전송하지 않음**(스푸핑 방지). 서버가 JWT에서 테넌트를 도출.

**에스케이프 해치:** 데이터 레지던시/격리를 요구하는 엔터프라이즈 테넌트는 나중에 **전용 DB로 승격**. 앱은 이미 모든 쿼리를 `tenant_id`로 스코프하므로, 코드 경로는 동일하고 **커넥션 라우팅(테넌트→DB 매핑 카탈로그)만** 바꾸면 된다. "기본은 풀링, 필요 시 격리"라는 현대 SaaS 표준 패턴.

```sql
-- 예: RLS 정책 (모든 테넌트 스코프 테이블에 적용)
alter table projects enable row level security;
create policy tenant_isolation on projects
  using (tenant_id = (auth.jwt() ->> 'tenant_id')::uuid);
-- 복합 인덱스는 tenant_id를 선두로
create index idx_projects_tenant on projects (tenant_id, status);
```

## 2. 인증 / 인가

### 2-1. 인증 (Authentication)

| 방식 | 대상 | 구현 |
| --- | --- | --- |
| 이메일/매직링크·비밀번호 | 일반 사용자 | Supabase Auth 기본 |
| 소셜 OAuth | 국내 사용자 | Google + **Kakao/Naver**(국내 B2B 필수) |
| 조직 SSO (SAML/OIDC) | 엔터프라이즈 | Supabase SSO(유료) 또는 WorkOS/Clerk 연동 |
| SCIM 프로비저닝 | 대형 고객 | 후순위(WorkOS) |

- **멀티조직 소속**: 한 사용자가 여러 테넌트에 속할 수 있음 → `memberships(user_id, tenant_id, role, status)`. 로그인 후 **활성 테넌트 선택**, JWT 커스텀 클레임에 `tenant_id`+`role` 주입(Supabase Auth Hook).
- `createdBy`, `reviewerId`, `approvedBy`는 **인증된 신원에서 서버가 주입**. 현재 하드코딩(`'current-user'`, `reviewerId: '1'`, `reviewers: ['exec-001']` — `/home/user/clubschool/hooks/useDataStore.ts`, `/home/user/clubschool/components/ProjectReview.tsx`)을 제거.

### 2-2. 인가 (RBAC) — 시스템 역할을 직무와 분리

권한 역할(Owner/Admin/Editor/Viewer)은 `Member.role`(직무명)과 **별개 개념**이다. 승인 워크플로우(`draft→review→approved`)와 결합한다.

| 액션 | Owner | Admin | Editor | Viewer |
| --- | --- | --- | --- | --- |
| 조직 삭제·소유권 이전·과금 | ✅ | ❌ | ❌ | ❌ |
| 멤버/초대 관리, 조직 설정(그룹·캘린더·단가) | ✅ | ✅ | ❌ | ❌ |
| 프로젝트 생성·수정, allocation 편집 | ✅ | ✅ | ✅ | ❌ |
| 검토 제출(draft→review) | ✅ | ✅ | ✅ | ❌ |
| 승인/반려(review→approved) | ✅ | ✅ | ❌ | ❌ |
| 대시보드·분석 조회 | ✅ | ✅ | ✅ | ✅ |
| 비용/단가(민감정보) 조회 | ✅ | ✅ | 설정에 따라 | ❌(마스킹) |

- **서버가 권위**: RLS 정책 + API 가드에서 강제. 클라이언트(`ViewRenderer`/`Navigation`)의 역할 게이트는 UX용일 뿐 보안 경계가 아님.
- **감사 로그**: 승인·삭제·단가 변경 등은 `audit_logs(tenant_id, actor_id, action, target, before, after, ts)`에 기록.

### 2-3. 초대 플로우

```
Admin: 이메일 입력 + 역할 지정 (+ 기존 Member 레코드 연결/신규 생성)
  → invitations(token, email, role, expires_at, status=pending) 생성 + 메일 발송
초대받은 사람: 가입/로그인(이메일 or OAuth) → 초대 수락
  → memberships(user_id, tenant_id, role, status=active) 생성, invitation=accepted
옵션: 검증된 회사 도메인 → 자동 가입(기본 Viewer/Editor)
엔터프라이즈: SCIM으로 자동 프로비저닝/디프로비저닝
```

## 3. 데이터 계층 전환: localStorage → API + DB (`useDataStore` 인터페이스 유지)

핵심 레버리지는 **컴포넌트가 데이터 출처를 모르는** 현재 구조다. `backend.md` 지침대로 **시그니처를 유지하고 내부만 교체**한다.

### 3-1. 추상화: `DataSource` 인터페이스

`useDataStore`가 직접 localStorage를 만지는 대신, 뒤에 `DataSource`를 둔다. 구현 2종을 플래그로 교체.

```ts
// 두 구현이 동일 시그니처를 만족 → useDataStore는 구현을 모름
interface DataSource {
  listProjects(): Promise<Project[]>;
  addProject(draft: ProjectDraft): Promise<Project>;
  updateAllocation(id: string, patch: Partial<ProjectAllocation>): Promise<ProjectAllocation>;
  // ...members/manmonths CRUD 동일
  getAggregates(period: string): Promise<{        // 파생계산은 서버가 계산
    dashboardStats: DashboardStats;
    utilizationData: UtilizationData;
    groupUtilization: GroupUtilization[];
    groupSummary: GroupSummary[];
  }>;
}
class LocalStorageDataSource implements DataSource { /* 현행 로직 이관 */ }
class ApiDataSource implements DataSource { /* fetch/RPC, 토큰 첨부 */ }
```

`useDataStore`는 이 위에서 **동일한 반환 형태(state + CRUD 함수 + 파생값)**를 유지한다. 컴포넌트는 그대로.

### 3-2. 동기 → 비동기 전환 (현행 대비)

| 관심사 | 현행(localStorage) | 목표(API+DB) |
| --- | --- | --- |
| 저장소 | 브라우저 localStorage | Postgres(테넌트 스코프) + localStorage는 캐시로 강등 |
| CRUD 반환 | 동기 `void`, `setState` | **비동기 Promise**, 낙관적 업데이트 + 서버 확정으로 재조정 |
| 서버 상태 관리 | 직접 `useState`+`useEffect` | **TanStack Query/SWR**로 캐시·무효화·롤백(도입 권장) |
| ID | `Date.now()+Math.random()` | **서버 발급 UUID**, 클라는 임시 낙관 ID → 응답 시 치환 |
| 파생계산 | 매 렌더 클라 계산(O(P×A)), 버그로 목데이터 고정 | **서버 계산(SQL 뷰/RPC)**, 클라는 표시만 |
| 테넌트 | 없음 | JWT에서 서버 도출(클라 미전송) |
| 정합성 | 클라 상태 직접 변형 + clamp | 서버 도메인 규칙(맨먼스 0~1, 가동률 0~100, 초과투입 검증) |
| 동시성 | 없음 | `updated_at`/버전 + 낙관적 동시성(충돌 시 롤백) |

- **파생값 서버 이전 이유**: (1) 다중 사용자 간 일관성, (2) 재무 수치 단일 진실·감사가능성, (3) 대규모 테넌트 성능, (4) 단가/비용 권한 보호. 맨먼스↔가동률 환산·유휴비용·그룹 집계 로직을 **Postgres 뷰 또는 RPC(SQL)로 리프트-앤-시프트**하고, 계산 파라미터(근무일 22, 시간 8, 기본단가 70000 등 — 현재 하드코딩)를 **테넌트 설정에서 주입**한다.
- **점진 마이그레이션 가능**: 플래그로 테넌트/화면별로 `ApiDataSource`를 켜며, 문제 시 `LocalStorageDataSource`로 즉시 롤백.

### 3-3. API 형태

- **CRUD**: Supabase 자동 REST(PostgREST) + RLS로 대부분 커버. 단, **집계/비용/승인 같은 권위적 로직은 얇은 서버 레이어(Edge Function / Route Handler)로** 감싼다(재무 계산을 클라에 노출하지 않기 위해).
- **집계 엔드포인트 예**: `GET /api/aggregates?period=2026-07` → 서버가 RLS 스코프로 계산해 `dashboardStats` 등 반환.

## 4. 프로비저닝 · 격리 · 과금 미터링 훅

### 4-1. 테넌트 프로비저닝 (온보딩)

```
가입 → 트랜잭션으로 { tenants + Owner membership } 생성
온보딩 위저드:
  ① 조직/그룹 정의 (하드코딩 유니온 planning|design|... → 테넌트별 group 마스터 테이블로 승격)
  ② 멤버·직무·시간단가 등록
  ③ 근무 캘린더(근무일/시간)·회계연도·기준월·목표 가동률(현 90%)
  ④ 통화/로케일/타임존 (현재 '원' 고정 → 설정화)
초기 상태: 빈 상태(empty state). 샘플 데이터는 선택적 '체험 데이터'로만.
```

기존 목데이터(`/home/user/clubschool/data/mockData.ts`)는 시드가 아니라 **선택적 샘플**로 강등. 기존 localStorage 사용자는 `exportData` JSON → 서버 import 엔드포인트로 **첫 테넌트에 이관**.

### 4-2. 격리 강제 (체크리스트)

- 모든 테이블 `tenant_id NOT NULL` + FK, 복합 인덱스 선두 `tenant_id`.
- RLS 정책 전 테이블 적용, 요청마다 JWT 기반 테넌트 컨텍스트.
- 리포지토리 계층 `tenant_id` 필터(2중 방어).
- **CI에 교차테넌트 접근 차단 테스트**(테넌트 A 토큰으로 B 데이터 조회 시 0건) 필수.

### 4-3. 과금 미터링 훅

| 미터링 차원 | 이벤트 발생 지점 | 용도 |
| --- | --- | --- |
| 활성 멤버(시트) | membership add/remove | **주 과금 단위** |
| 프로젝트 수 | project create/archive | 플랜 한도 |
| API 호출/스토리지 | 게이트웨이/스토리지 | 남용 방지·상위 플랜 |

- 변경 지점에서 `usage_events(tenant_id, metric, quantity, ts)` 적재 → 주기적 롤업.
- **Stripe(글로벌 표준) 또는 Paddle(부가세/해외결제 대행 유리)** 연동. 플랜별 한도 미들웨어로 생성 전 쿼터 검사.

| 플랜 | 멤버 한도 | 기능 | 격리 |

## 6. 트레이드오프 총평 & 최종 권고

- **격리**: 격리 강도만 보면 DB-per-tenant가 최고지만, 이 제품의 소데이터·다수테넌트·소규모운영 조건에서는 **비용/운영 오버헤드가 이득을 압도**한다. **공유 DB+RLS로 시작하고, 규제 고객만 전용 DB로 승격**하는 하이브리드가 유일하게 합리적. (앱이 이미 전 쿼리를 `tenant_id`로 스코프하도록 만들면 승격이 커넥션 라우팅 문제로 축소된다.)
- **스택 응집도 vs 제어권**: Supabase는 초기 속도·응집도를 주고 커스텀 자유도를 약간 희생한다. 이 단계에서는 **속도가 정답**이며, 재무 권위 로직만 얇은 서버 레이어로 감싸 Supabase의 "클라 직결" 리스크를 상쇄한다.
- **전환 리스크 최소화**: `useDataStore` 시그니처 유지 + `DataSource` 플래그 교체가 **회귀 위험을 국소화**한다. 단, **P1의 정합성 버그 수정은 협상 불가한 선행조건**(실데이터에서 가동률·비용이 목데이터로 고정되면 재무 신뢰가 무너짐).
- **인가 설계의 핵심**: 시스템 역할을 직무(`role`)와 분리하고, 서버(RLS+가드)를 단일 권위로 삼는 것. 클라 게이트는 UX일 뿐.

**최종 권고 한 줄**: *Vercel(프론트) + Supabase Seoul(공유 Postgres+Auth+RLS)로, `tenant_id` row-level 격리와 Owner/Admin/Editor/Viewer RBAC를 깔고, `useDataStore`를 `DataSource` 추상화로 감싸 파생계산을 서버로 이전하며, 시트 기반 미터링으로 과금하되 엔터프라이즈는 전용 DB로 승격하는 하이브리드로 간다.*
