## 2) 도메인 데이터 모델 (`types/index.ts`)

핵심 엔티티는 4개(Member / Project / ProjectAllocation / MemberManmonth), 나머지는 대부분 파생·집계·분석용 타입입니다.

**핵심 엔티티 · 필드 · 관계**

| 엔티티 | 주요 필드 | 관계 |
| --- | --- | --- |
| `Member` | `id, name, role, group(5종), email, avatar?, hourlyRate?(원)` | 1 Member — N Allocation, 1 Member — 1 MemberManmonth |
| `Project` | `id, name, status(7종), startDate, endDate, description, allocations[], createdBy, reviewers[], approvedBy?, approvedAt?, reviewComments?` | 1 Project — N Allocation, N ReviewComment |
| `ProjectAllocation` | `id, memberId, projectId, startDate, endDate, actualEndDate?, utilizationRate(0~100), role, status(active/completed/withdrawn), withdrawalReason?` | Member↔Project N:N 연결(투입) |
| `MemberManmonth` | `memberId, lastMonthActual, thisMonthEstimated, availableManmonth, utilizationRate(%)` | Member와 1:1, 맨먼스 0~1 범위 |
| `ReviewComment` | `id, reviewerId, comment, type(approval/rejection/request_change), createdAt` | Project에 임베드 |

**열거형(Enum) 값**
- `group`: `planning | design | publishing | management | executive`
- `Project.status`: `draft → review → approved → planning → in-progress → completed`(또는 `on-hold`)
- `Allocation.status`: `active | completed | withdrawn`

**입력/드래프트 타입**: `ProjectDraft`(생성 폼), `TeamMemberDraft`(팀 구성 항목, `isRequired` 포함).

**파생/집계·분석 타입**(상태로 저장 안 되고 계산으로 생성): `DashboardStats`, `GroupSummary`, `UtilizationData`(지난달/이번달/비교, 유휴비용 포함), `GroupUtilization`, `MonthlyUtilizationTarget`, `YearlyUtilizationSummary`, `YearlyGroupUtilization`, `UtilizationInsight`, `MonthlyManmonth`, `MemberHistory`, `MemberPerformance`, `OptimizationRecommendation`, `QuarterlyReport`.

**핵심 계산 규칙**
- 맨먼스 1.0 = 1인 1개월 풀가동. allocation의 `utilizationRate/100`으로 환산.
- 비용 = `근무시간(22일×8h=176h) × hourlyRate`. 유휴비용 = `(1-가동률)×176h×rate`.
- 맨먼스는 0~1, 가동률은 0~100으로 clamp(`useDataStore`의 `updateMemberManmonthsForAllocations`).

## 3) 상태 · 저장 방식

**단일 저장소**: `hooks/useDataStore.ts` (모든 뷰에 `dataStore` prop으로 주입, `App.tsx`에서 1회 생성).

- **원천 상태 4종**(`useState`): `members`, `projects`, `allocations`, `memberManmonths`.
- **localStorage 동기화**: 키는 `STORAGE_KEYS`(`pm_members` / `pm_projects` / `pm_allocations` / `pm_manmonths`). 각 상태마다 `useEffect`로 저장, 초기값은 `loadFromStorage`로 로드(실패 시 mock fallback). 입출력은 `try/catch`로 감쌈.
- **ID 생성**: `generateId(prefix)` 헬퍼(timestamp+random). 직접 `Math.random` 산재 금지 규칙 준수.
- **CRUD**: `addMember/updateMember/deleteMember`, `addProject/updateProject/deleteProject`, `addAllocation/updateAllocation/removeAllocation`, `updateMemberManmonth`.
- **정합성 유지**: 멤버 삭제 시 관련 allocation·manmonth 동시 제거. allocation 추가/삭제/가동률·상태 변경 시 `updateMemberManmonthsForAllocations`로 맨먼스 재계산(불변 업데이트).
- **파생 데이터 노출**: `projects`는 `getProjectsWithAllocations()`로 allocation을 join한 결과를 반환. `dashboardStats`, `utilizationData`, `groupUtilization`, `groupSummary`를 계산해 함께 반환.
- **유틸**: `resetToDefaultData`(기본값 초기화), `exportData`(JSON 다운로드), `importData`.

**주의(발견된 리스크 3건, 사실 기반)**
1. **파생 계산이 라이브 상태와 분리됨**: `calculateUtilizationData`, `calculateGroupUtilization`, `getGroupSummary`(모두 `data/mockData.ts`)는 인자를 받지 않고 **모듈 레벨 `mockMemberManmonths`/`mockMembers`를 직접 참조**합니다. `useDataStore`의 래퍼는 `useCallback` 의존성에 `memberManmonths`를 넣었지만 실제 계산에는 사용하지 않습니다. → localStorage에 저장된 편집 결과가 `utilizationData`/`groupUtilization`/`groupSummary`에 **반영되지 않음**. `dashboardStats`만 라이브 상태 기반.
2. **mock 데이터의 비결정성**: `mockMemberManmonths`(가동률 ±10% 변동)와 `mockAllocations`(utilizationRate)가 모듈 로드 시 `Math.random`으로 생성됨 → 최초 로드(저장 전)마다 값이 달라짐.
3. **그룹 라벨-데이터 불일치**: `publishing` 그룹(8명)이 mock에서 `dev-xxx` id·"개발자" role로 채워져 있어 도메인 라벨(퍼블리싱)과 실제 데이터(개발) 명명이 어긋남.

## 0. 한 줄 요약
현재 앱은 **"한 회사(56명, 5그룹, 본부장 1명)를 한 브라우저에서 보는 단일 사용자 도구"** 로 설계되어 있다. 테넌트·서버·인증·기준데이터 개념이 전부 부재하지만, **도메인 모델·계산 규칙·`useDataStore` 단일 진입점·UI 레이어**는 그대로 살릴 수 있어 전환 비용 대비 재사용 가치가 높다.

## 1. 한계 → SaaS 요구사항 매핑

### 1-1. 단일 테넌트 가정 (회사가 하나뿐이라는 전제)
**근거**
- 도메인 타입 어디에도 `tenantId`/`organizationId`가 없다. `Member`, `Project`, `ProjectAllocation`은 회사 소속 정보를 갖지 않는다 (`/home/user/clubschool/types/index.ts:1-45`).
- 조직 구조가 타입에 **하드코딩된 리터럴 유니온**으로 박혀 있다: `group: 'planning' | 'design' | 'publishing' | 'management' | 'executive'` (`types/index.ts:5`)가 15곳 이상에서 반복. 회사마다 다른 조직도를 표현할 수 없다.
- "56명", "본부장 1명" 가정이 데이터·UI·문안 전반에 고정 (`data/mockData.ts:7-58`, `README.md:15`, CLAUDE.md).
- 저장 키가 전역 단일이다: `pm_members`, `pm_projects`… (`hooks/useDataStore.ts:12-17`). 테넌트 네임스페이스가 없다.

**→ SaaS 요구사항**
- 모든 엔티티에 `tenantId`(조직 식별자) 추가 → 타입·DB 스키마·모든 쿼리에 **테넌트 스코프** 강제 (row-level scoping / RLS).
- `group`을 하드코딩 유니온에서 **테넌트별 설정 테이블**(조직/그룹 마스터)로 승격. "5그룹·본부장 1명"은 기본값일 뿐 가변이어야 함.
- 테넌트 간 데이터 격리 보장(한 회사가 다른 회사 데이터를 조회 불가). 저장 키/쿼리 네임스페이스를 `tenantId` 기준으로 분리.

### 1-2. localStorage 저장 (서버/DB 부재)
**근거**
- 데이터가 브라우저 localStorage에만 존재. 로드/저장 전부 `localStorage.getItem/setItem` (`hooks/useDataStore.ts:20-36`), 상태 변경 시마다 `useEffect`로 동기화 (`:61-75`).
- 공유·백업 수단이 **JSON 파일 다운로드/업로드**뿐 (`exportData`/`importData`, `:298-327`). 기기·브라우저가 바뀌면 데이터가 사라지고, 두 사람이 같은 데이터를 볼 수 없다.
- ID 생성이 `Date.now()+Math.random()` (`:39-43`) — 전역 유일성 보장 없음, 동시 생성 시 충돌 가능.

**→ SaaS 요구사항**
- **백엔드 + 영속 DB** 도입(PostgreSQL 등). localStorage는 캐시/오프라인 보조로 강등.
- 서버 REST/RPC API로 CRUD 전환. 다행히 `.claude/rules/backend.md`가 이미 "`useDataStore` 시그니처 유지 + 내부 구현만 API로 교체" 전략을 명시 → **컴포넌트 수정 없이** 데이터 계층만 교체 가능한 설계 지향이 이미 있음.
- ID는 서버 발급 UUID/시퀀스로. 클라이언트 `generateId` 폐기 또는 임시 낙관 ID로만 사용.
- 다중 사용자 동시 편집 대비: `updatedAt`/버전 필드, 낙관적 동시성 제어(롤백 경로), 소프트 삭제·감사 로그(audit trail) 추가.

### 1-3. 인증·권한 부재
**근거**
- 로그인/세션/사용자 식별 개념이 전무. 현재 사용자가 **문자열 리터럴로 위조**되어 있다: `createdBy: 'current-user'` (`hooks/useDataStore.ts:169`), `reviewerId: '1' // 현재 사용자 ID` (`components/ProjectReview.tsx:114`), 기본 리뷰어 `reviewers: ['exec-001']` 하드코딩 (`useDataStore.ts:170`).
- 권한(RBAC)이 없다. `Member.role`은 "시니어 기획자" 같은 **직무명 문자열**일 뿐 접근 권한이 아니다 (`types/index.ts:4`, `mockData.ts:33`).
- 네비게이션·뷰가 누구에게나 전부 노출된다. `ViewRenderer`는 역할 검사 없이 모든 뷰를 라우팅하고(`components/ViewRenderer.tsx:100-142`), 프로젝트 승인/삭제/멤버 삭제도 권한 게이트가 없다.

**→ SaaS 요구사항**
- **인증**(로그인, 세션/JWT, SSO/OAuth·이메일) 도입. `createdBy`/`reviewerId`/`approvedBy`는 인증된 사용자 신원에서 주입.
- **인가/RBAC**: 시스템 역할(본부장/사업관리/멤버/뷰어 등)을 직무(`role`)와 분리한 별도 개념으로 정의. 프로젝트 생성·검토·승인·멤버 관리 액션에 서버·클라이언트 양쪽 권한 검사.
- 테넌트 멤버십(User ↔ Tenant ↔ Role) 모델, 초대·온보딩 플로우. 승인 워크플로우(`draft→review→approved`)를 실제 권한과 결합.
- 감사 로그(누가 언제 무엇을 승인/변경).

### 1-4. 목데이터 하드코딩
**근거**
- 56명 구성원이 코드로 생성됨(`Array.from`으로 기획32·디자인14·퍼블8 + 본부장/관리 각1), 직무·시간단가(`hourlyRate`)까지 상수로 박힘 (`data/mockData.ts:8-58`).
- 프로젝트 3건이 id `'1','2','3'`으로 고정 (`mockData.ts:99-133`), 맨먼스·분기·월별·성과·최적화 추천이 전부 정적 배열 (`mockData.ts:136-515`).
- **초기·리셋 데이터가 이 목데이터**다: `useState(() => loadFromStorage(KEY, mockMembers))` (`useDataStore.ts:47-58`), `resetToDefaultData()`가 목데이터로 되돌림 (`:291-296`).
- 맨먼스 초기값이 `Math.random()` 기반(`mockData.ts:145-155`) → 매번 값이 달라지고 재현 불가.

**→ SaaS 요구사항**
- 목데이터를 **테넌트별 실데이터**로 대체. 신규 테넌트는 **빈 상태(empty state)** 로 시작하고, 시드/샘플 데이터는 선택적 "체험 데이터" 로만 제공.
- 시간단가·직무·그룹 등은 상수가 아니라 테넌트 관리 화면에서 CRUD 되는 **마스터 데이터**로.
- 분석/추천용 정적 배열(`mockMonthlyData`, `mockQuarterlyData`, 최적화 추천 등)은 실데이터 집계로 산출되도록 대체. 랜덤 초기화 제거(결정론적/실측 기반).

### 1-5. 기준데이터(마스터) 셋업 부재
**근거**
- 회사가 자기 조직을 구성할 온보딩/설정 화면이 없다(`constants/views.ts` 뷰 목록에 조직·정책 설정 뷰 없음, `ViewRenderer` 분기에도 없음).
- 계산 상수가 코드에 고정: 월 근무일 `22`, 일 근무시간 `8`, 기본 시간단가 `70000` (`data/mockData.ts:171-172, 187, 254`). 회사마다 다른 근무 캘린더·기본단가를 반영할 수 없다.
- 기간 개념이 없다. "지난달/이번달"은 실제 날짜가 아니라 `MemberManmonth`의 두 스칼라 필드일 뿐(`types/index.ts:67-73`) — 회계연도/월 마감/기준월 선택이 불가.
- 목표 가동률·월별 타깃도 정적(`MonthlyUtilizationTarget`이 하드코딩된 컴포넌트 데이터).

**→ SaaS 요구사항**
- 테넌트 **온보딩 위저드**: 조직/그룹 정의 → 멤버·직무·단가 등록 → 근무 캘린더(근무일/시간)·회계연도·목표 가동률 설정.
- 계산 파라미터(근무일, 시간, 기본단가, 목표치)를 **테넌트 설정 엔티티**로 외부화.
- 실제 **기간(period) 모델** 도입: `YYYY-MM` 기준월, 월 마감(lock), 시점별 스냅샷. "지난달/이번달"을 실제 날짜 계산으로 대체.
- 통화·로케일·타임존 설정(현재 "원(₩)" 고정).

### 1-6. 파생 계산의 서버화 필요성
**근거**
- 파생 지표(대시보드 통계·가동률·그룹 집계·유휴비용)가 **매 렌더 클라이언트에서 계산**된다: `dashboardStats: getDashboardStats()` 등을 return에서 직접 호출 (`useDataStore.ts:329-341`), `getProjectsWithAllocations()`도 매 렌더 O(projects×allocations) (`:78-83, 332`).
- **정합성 버그(전환 전 반드시 수정)**: `calculateUtilizationData`/`calculateGroupUtilization`/`getGroupSummary`는 인자 없이 **모듈 상수 `mockMembers`/`mockMemberManmonths`를 직접 읽는다** (`mockData.ts:170, 184, 234, 239-240, 518-523`). 그런데 `useDataStore`는 이들을 `memberManmonths` 상태에 의존하는 것처럼 감싼다(`useDataStore.ts:106-116`). 즉 **사용자가 멤버/투입을 수정해도 가동률·비용 분석은 초기 목데이터 기준으로 고정**된다. 실데이터로 가면 치명적.
- 금액 계산(총비용·유휴비용)이 클라이언트에서 이뤄지고(`mockData.ts:189-203`), 맨먼스 재계산 `updateMemberManmonthsForAllocations`가 클라이언트 상태를 직접 변형하며 clamp로 초과투입을 가림(`useDataStore.ts:251-281`) — 여러 프로젝트 합산 초과·비용 오차의 근원.

**→ SaaS 요구사항**
- 집계·비용·맨먼스 환산 같은 **파생 계산을 서버로 이전**. 이유: (1) 다중 사용자 간 **일관성**(같은 숫자를 모두가 봄), (2) **정확성/감사가능성**(재무 수치는 서버가 단일 진실), (3) **성능**(테넌트 수천 멤버 규모에서 클라이언트 집계는 비현실적), (4) **보안**(단가·비용을 권한 없는 사용자에게 노출 방지).
- 서버 계산 결과를 API로 내려주고 클라이언트는 표시만. 무거운 집계는 사전 집계(materialized)/캐시.
- 계산 파라미터(근무일·단가 등)를 테넌트 설정에서 주입받아 계산 함수 인자화 → 모듈 상수 의존 제거(위 버그 해소).
- 맨먼스·가동률 범위 clamp(0~1 / 0~100)와 초과투입 검증을 서버 도메인 규칙으로 격상.

## 3. 전환 우선순위 권고 (핸드오프용)

1. **테넌시 모델 먼저**: `types/index.ts`에 `Tenant`/`User`/`Membership`/`Role` 추가, 전 엔티티에 `tenantId`. (단일 진실 원천 변경 → `useDataStore` 시그니처 영향 최소로 설계)
2. **정합성 버그 선수정**: 파생 계산 함수의 모듈 상수(`mockMembers`/`mockMemberManmonths`) 직접 참조를 인자 주입으로 전환(`data/mockData.ts`, `useDataStore.ts:106-116`). 실데이터 이전의 전제 조건.
3. **`useDataStore` 내부를 API 클라이언트로 교체**(시그니처 유지) + 백엔드/DB 구축. 파생 계산은 서버로.
4. **인증·RBAC** 도입 후 `createdBy`/`reviewerId`/승인 액션을 실 신원·권한과 결합.
5. **테넌트 온보딩/기준데이터 설정 화면** 추가(조직·그룹·근무캘린더·단가·목표·통화). 목데이터는 선택적 샘플로 강등.

**영향받는 핵심 파일/타입**: `types/index.ts`(계약), `hooks/useDataStore.ts`(데이터 흐름·단일 진입점), `data/mockData.ts`(계산·시드), `components/ViewRenderer.tsx`+`constants/views.ts`(라우팅), `components/ProjectReview.tsx`(승인 신원).

**미해결/판단 필요(가정 금지)**: 테넌트 격리 방식(단일 DB+RLS vs 스키마 분리), 조직 계층 깊이(현재 2단계 고정 vs 가변), 요금/구독 모델 유무, 데이터 마이그레이션(기존 localStorage 사용자 이관 여부) — 이들은 PO/사용자 결정이 필요하다.
