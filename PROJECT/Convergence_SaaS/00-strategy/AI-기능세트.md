# AI 기능 세트

> 컨버전스 SaaS(과제 #3) · 팀 워크플로우 산출

# 프로젝트 수행본부 대시보드 — 도메인 특화 AI 기능 세트 설계 (데이터분석/PO 관점)

## 0. 설계 전제 — "AI가 핵심 가치"가 되려면 두 가지를 지켜야 한다

**원칙 A — Claude 대체불가성 기준.** 기능에서 Claude(LLM)를 빼도 제품이 성립하면 그건 "분석 대시보드 + AI 장식"이지 AI 서비스가 아니다. 진짜 AI 코어는 **자연어 이해·서사 생성·비정형 추론**이 값어치의 중심인 것(F4, F5)이고, 나머지(F2·F3·F6·F8)는 **결정론 엔진 + Claude 서술** 조합, 예측군(F1·F7)은 **간단 ML/통계 + Claude 해설**이다. 이 구분을 정직하게 해야 우선순위가 선다.

**원칙 B — 정확성 가드레일(재무 대시보드의 생명).** Claude에게 가동률·비용 숫자를 **직접 계산시키지 않는다.** 앱(`useDataStore`/서버)이 결정론적으로 집계하고, Claude는 (1) 무엇을 집계할지 **쿼리 스펙(JSON)** 을 만들거나 (2) 이미 계산된 숫자 위에 **서사·원인가설·액션**만 얹는다. 이 아키텍처가 환각 리스크를 구조적으로 차단한다.

**핵심 데이터 제약 (우선순위를 지배함).** 현재 데이터엔 **시계열 이력이 없다.** `MemberManmonth`는 `lastMonthActual`/`thisMonthEstimated` 두 스칼라뿐이고, "지난달/이번달"이 실제 날짜가 아니다(SaaS 진단 1-5). 또한 파생계산이 mock 상수를 직접 참조하는 정합성 버그가 남아 있다(진단 1-6). → **예측·리스크ML(F1·F6-ML·F7)은 "기간(period) 스냅샷 모델" 구축 전까지 불가.** 반면 **현재 계산값만으로 즉시 되는 것(F5·F4·F3·F8·F2)** 이 MVP 후보다.

## 2. AI 접근의 정직한 분류 — "무엇이 진짜 AI 코어인가"

| 계층 | 기능 | Claude를 빼면? | SaaS AI 정당성 |
|------|------|---------------|---------------|
| **A. Claude 대체불가 코어** | F4, F5 | 제품이 성립 안 함(자연어 이해·서사가 값어치의 중심) | **AI가 곧 제품.** MVP는 여기서 뽑아야 함 |
| **B. 결정론 엔진 + Claude 서술** | F2, F3, F6(규칙판), F8 | 기능은 남지만 "왜/무엇을 해야"의 설명력·조치력이 사라짐 | AI가 실행가능성(actionability)을 부여 — 확산 단계 |
| **C. ML/통계 + Claude 해설** | F1, F6(ML판), F7 | 예측은 남고 해설만 사라짐 | AI 정당성은 있으나 **데이터 이력 축적이 선행 조건** |

포인트: **A계층만이 "지금 데이터로, Claude가 없으면 못 만드는" 기능**이다. C계층은 야심차지만 시계열 인프라가 없어 지금은 데모밖에 못 만든다. MVP는 A에서, 확산은 B에서, 장기 해자는 C에서.

## 3. 우선순위 — MVP vs 차기

평가축: **가치(V)** · **AI 코어성(Claude 대체불가, C)** · **데이터 준비도(현재 데이터로 가능=●)** · **난이도(D, 낮을수록 좋음)**.

| 순위 | 기능 | V | C | 데이터 준비도 | D | 배치 |
|------|------|---|---|-------------|---|------|
| 1 | **F5 주간 인사이트 브리핑** | 상 | **최상** | ● 즉시 | 낮 | **MVP** |
| 2 | **F4 자연어 질의→리포트** | 상 | **최상** | ● 즉시 | 중 | **MVP** |
| 3 | **F3 유휴·과부하 경보** | 중 | 중 | ● 즉시 | 낮 | MVP 번들(F5 입력원) |
| 4 | F8 비용 최적화 시뮬 | 중상 | 중 | ● 즉시 | 중 | 차기 1 |
| 5 | F2 인력 최적 배치 추천 | 상 | 중 | ● 즉시 | 중 | 차기 1 |
| 6 | F6 리스크/지연 예측(규칙판) | 상 | 중 | ◐ 일부(이력 부족) | 중 | 차기 2 |
| 7 | F1 가동률·수요 예측 | 상 | 상 | ○ **불가**(스냅샷 선행) | 높 | 차기 2(인프라 후) |
| 8 | F7 채용·외주 보조 | 중 | 상 | ○ **불가**(F1 의존) | 높 | 차기 3 |

**MVP 확정: F5 + F4 (+ F3을 F5 번들로).**
- 둘 다 **현재 계산값만으로 동작** → 백엔드/시계열 인프라 없이 착수 가능.
- 둘 다 **Claude 대체불가** → "AI가 핵심"임을 첫 릴리즈에서 즉시 증명.
- F5(낮음)로 빠른 가치·리텐션, F4(중간)로 차별화. F3은 규칙 코어라 저비용이며 F5 브리핑의 "리스크" 섹션을 채워 시너지.
- **차기 1(F8·F2)** 은 결정론 엔진 위 Claude 서술로 확장, **차기 2(F6·F1)** 는 기간 스냅샷 모델 구축과 함께.

## 4. MVP 2종 구체 설계

### F5 — 자동 인사이트 브리핑 (1순위, 난이도 낮음)
- **파이프라인:** 앱이 지난달↔이번달 지표 델타 계산(가동률·유휴비용·그룹편차·상태전이·F3 경보) → 델타 JSON을 Claude에 전달 → Claude가 **핵심변화 3 / 리스크 2 / 권장액션 3** 을 한국어로 작성 → 브리핑 카드로 렌더 + (선택) 이메일/슬랙.
- **가드레일:** 프롬프트에 "제공된 숫자만 사용, 새 수치 계산·창작 금지"를 명시. 모든 수치는 앱이 채운 값을 그대로 인용.
- **모델:** 요약 태스크라 저비용/경량 모델로 충분(브리핑은 저지연·저비용이 리텐션에 유리). 실제 모델·비용은 도입 시점에 검증 후 확정.
- **가치 지표(KPI):** 브리핑 열람률, 브리핑 발 액션 클릭(예: "이 인력 재배치") 전환율, 주간 재방문(WAU).

### F4 — 자연어 질의 → 리포트/차트 (2순위, 난이도 중간)
- **파이프라인:** 질문 + 스키마 메타 → Claude가 **쿼리 스펙(집계대상·필터·그룹·기간·차트타입) JSON** 생성(structured output/tool use) → 앱의 **안전한 결정론 집계기**가 dataStore에서 실행 → 결과를 Recharts 스펙 + 해설 3줄로 Claude가 렌더.
- **가드레일:** Claude는 **스펙만** 생성하고 **숫자는 계산하지 않음.** 화이트리스트 필드/집계함수로 스펙 검증(임의 코드 실행 금지). 스펙→집계는 순수 함수.
- **모델:** 자연어→구조화 매핑은 정확도가 중요하므로 상위 추론 모델 권장(스펙 검증 레이어로 오류 흡수).
- **UI:** 기존 `VIEW_NAMES` → `ViewRenderer`에 `ai-analyst` 뷰 1개 추가, `dataStore` prop 재사용(프론트 규칙 준수). "이 차트 저장"으로 대시보드 위젯화 → 반복 가치.
- **KPI:** 질의 성공률(사용자가 결과 채택), 질의당 개발요청 대체 건수, 저장된 커스텀 차트 수.

## 5. 전제조건 / 리스크 (PO 판단 필요)

1. **정합성 버그 선수정(차단 이슈):** 파생계산이 `mockMembers`/`mockMemberManmonths` 상수를 직접 참조(진단 1-6). **F4·F5·F3 모두 "라이브 데이터 기준 집계"를 전제**하므로, AI 착수 전 계산함수 인자 주입 전환이 필수. 안 고치면 AI가 mock 위에서 그럴듯한 거짓 브리핑을 생성한다.
2. **기간(period) 스냅샷 모델은 예측군의 열쇠:** F1·F6-ML·F7은 월별 스냅샷 시계열 없이는 불가. SaaS 전환의 "기간 모델 도입"과 **동일 인프라 의존** → 로드맵을 묶으면 효율적(예측은 스냅샷이 6~12개월 쌓인 뒤 유의미).
3. **Claude API 위치:** localStorage 단일 클라이언트에선 API 키를 클라이언트에 둘 수 없음(backend.md·보안). F4/F5의 Claude 호출은 **최소 서버 프록시(엣지 함수)** 가 필요 → SaaS 백엔드 도입과 자연스레 합류.
4. **결정: MVP를 "현재 앱 위 애드온"으로 낼지, "SaaS 백엔드와 함께" 낼지.** F5/F4 데모는 프록시만 있으면 현재 앱에도 얹히지만, 멀티테넌트·과금·이력축적을 노린다면 SaaS 백엔드 착수와 병행이 합리적. 이 범위는 PO/사용자 결정 사항(가정하지 않음).
