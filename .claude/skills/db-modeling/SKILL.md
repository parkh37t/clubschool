# DB 모델링 (ERD / 스키마)

도메인을 엔티티·관계로 모델링하고 정합성 제약을 정의합니다.

## 절차
1. **엔티티 도출**: 기능정의서에서 명사(리소스)를 추출합니다.
   - 이 도메인 기준 엔티티 예: `Member`, `Project`, `ProjectAllocation`,
     `MemberManmonth`(타입은 `types/index.ts`가 단일 원천).
2. **관계 정의**: 1:N / N:M과 카디널리티, 외래키를 정합니다(예: Project 1:N Allocation).
3. **속성/타입**: 각 필드의 타입·필수여부·기본값·단위를 명시(맨먼스 0~1, 가동률 0~100).
4. **정합성 제약**: 유니크/외래키/체크 제약, 캐스케이드 규칙(멤버 삭제 시 allocation·
     manmonth 동시 제거 등).
5. **인덱스/조회 패턴**: 자주 쓰는 조회를 기준으로 인덱스 후보를 제시.
6. **마이그레이션 메모**: 기존 데이터(localStorage/목 데이터) → 신규 스키마 이행 경로.

## 산출물 포맷
```md
## ERD (관계)
- Entity A 1:N Entity B (FK: ...)

## 스키마: <엔티티>
| 필드 | 타입 | 필수 | 제약/기본값 | 단위/설명 |
| --- | --- | --- | --- | --- |

## 정합성 규칙
- 캐스케이드 / 유니크 / 체크:
```

## 원칙
- 타입은 `types/index.ts`와 1:1로 맞춥니다(API 계약의 단일 원천).
- 경계값 clamp·캐스케이드 규칙을 빠짐없이 명시. 파괴적 마이그레이션은 사용자 확인.
- `api-design`(엔드포인트)과 짝으로 사용. 결과는 한국어로 작성.
