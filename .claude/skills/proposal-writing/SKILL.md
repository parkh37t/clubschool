# 제안서 작성

평가자가 점수를 줄 수 있는 제안서를 씁니다. 멋진 문장보다 **요구 대응·근거·실행 가능성**이 먼저입니다.

## 1. 브리프 고정 (쓰기 전에)
- 고객·사업명, 제출본/발표본 구분, 제출 기한·발표 시간, 분량·양식 제약, 평가 항목과 배점, 쓸 수 있는 실적·인력 자료.
- 모르는 값은 지어내지 않고 `가정` 또는 `미확인`으로 적어 둡니다.

## 2. 근거표 (조사 단계부터 이어 쓰기)
| 근거 id | 진술 | 상태 | 근거 종류 | 출처 위치 | 기준일 | 적용 범위 | 확인 필요 |
- 근거 id 는 `EV-001`부터 붙이고, 뒤 단계는 같은 id 를 가리킵니다. 새 근거는 다음 번호로 그 단계 산출물 끝 '근거표 추가분'에 덧붙입니다(번호를 다시 쓰거나 지어내지 않음).
- 상태는 여섯 값 가운데 하나입니다: `verified_fact`(범위·기준일까지 직접 확인) · `source_claim`(자료에 적혀 있으나 직접 확인 안 함) · `proposal`(이번 제안의 권고·목표) · `hypothesis`(관찰에서 나온 해석, 검증 필요) · `unresolved`(출처 없음·서로 어긋남·범위 불명) · `placeholder`(임시 문구·샘플 값).
- 문서에 적혀 있다는 것만으로 `verified_fact`로 올리지 않습니다. 어긋나는 주장은 원래 행을 지우지 않고 `unresolved` 행을 더합니다.

## 3. 요구·평가 대응표 (RFP 분석에서 이어받기)
| 요구 id | 원문 위치 | 요구 내용 | 평가 항목 | 대응할 장 | 근거(EV id) | 충족 상태 | 공백 | 제출 장표 id | 발표 장표 id | 백업 장표 id |
- RFP 요구는 하나도 빠뜨리지 않고 옮깁니다. 대응하지 못하는 요구는 `공백`으로 드러냅니다(숨기지 않음).
- 요구 id 는 원문 번호를 그대로 씁니다. 원문 번호가 없으면 `internal:`을 붙인 내부 id 를 씁니다.
- 장표 id 칸은 장표 구성안을 만든 뒤 채웁니다(역채움). 발표에서 빼는 요구는 `발표 제외`와 사유를 적습니다 — `발표 제외`는 `미대응`이 아닙니다.

## 4. 전략과 스토리
- **승부 메시지 1개**와 그것을 받치는 전략 2~4개. 각각 받치는 근거 id 를 적습니다.
- 스토리 흐름: 고객의 문제 → 성공 조건 → 왜 우리인가 → 무엇을 어떻게 → 완수·검증 방법 → 결정 요청.
- 목차는 평가 항목·배점 순서를 따르고, 배점이 큰 항목에 분량을 싣습니다. 회사 소개는 앞에 길게 두지 않습니다.

## 5. 장표 구성안 (구조 단계)
장표마다 한 줄씩:
| 장표 id | 평가자 질문 | 결론형 제목 | 근거 id(EV) | 도식 유형 | 담당 요구 id |
- 제목은 주제어("추진 전략")가 아니라 결론 문장("3단계로 나눠 6개월 안에 전환을 끝낸다")으로 씁니다.
- **제목만 이어 읽어도 주장이 이어져야** 구조 단계를 통과합니다.
- 근거표는 새로 만들지 않고 앞 단계 것을 이어 씁니다(빠진 근거만 보강).
- 구성안을 만든 뒤 대응표의 장표 id 칸을 역채웁니다(`대응표 역채움` 표 — 요구 id 마다 제출·발표·백업 장표 id, 없으면 `공백`).
- 견적이 아직 승인되지 않았으면 금액·M/M·인원은 숫자로 쓰지 않고 `「확정 필요」`로만 적습니다.

## 6. 본문 (본문 단계)
- 구성안 순서대로 씁니다. 장마다 결론 → 근거(EV id) → 실행 방법 → 검증 방법.
- 표준 장 구성 예: 사업 이해 · 추진 전략 · 수행 범위(포함/제외) · 일정(WBS·마일스톤) · 투입 인력 · 품질·리스크 관리 · 레퍼런스 · 평가 항목 대응표.
- 견적·투입 M/M 은 범위와 가정으로만 적고, 확정은 승인 절차를 따릅니다.

## 7. 발표본·발표 노트 (발표가 있을 때)
- 제출본을 기준으로 발표 흐름을 다시 짭니다. 제출본의 논리·수치·번호는 바꾸지 않고, 장표마다 `발표 / 백업 / 발표 제외`를 정합니다.
- 가용 설명 시간 = 배정 시간 − 질의응답 − 시연 − 전환·여유. 장마다 예상 초를 붙여 합계와 맞춥니다(모르는 값은 가정).
- 발표 노트는 장마다 네 줄: 전달할 핵심 문장 · 근거 설명 · 다음 장으로의 연결 · 예상 질문과 백업 장표 위치. 본문을 읽는 대본을 만들지 않습니다.
- 리허설을 실제로 하지 않았으면 `스크립트 검토`라고 적습니다.

## 8. 정합 (검수 전 스스로)
- 고객명·사업명·버전이 모든 쪽에서 같은지, 숫자·단위·합계가 맞는지, 자리표시(TBD·xx)가 남지 않았는지 확인합니다.
- 최종 판정은 작성자가 아니라 검수 담당(`proposal-review`)이 합니다.

## 9. 보완할 때 — 변경 기록
- 지적을 받아 고칠 때는 산출물 끝에 `변경 기록` 표를 남깁니다.
| CHG id | 지적 | 변경 전 | 변경 후 | 영향 위치 |
- 전략명·수치·요구 id 하나를 고치면 같은 값을 쓰는 다른 절·표·노트도 찾아 함께 고치고, 영향 위치에 적습니다. 고치지 못한 지적은 `미반영 — 이유`로 남깁니다.

## 작성 원칙
- 할 수 있는 것만 약속합니다. 완료·수주·효과를 과장하지 않습니다.
- 측정하지 않은 효과 수치("만족도 30% 향상")를 쓰지 않습니다. 대신 "기준선을 먼저 재고 같은 정의로 비교한다"처럼 검증 방법을 씁니다.
- 뜻이 비어 있는 수식어(혁신적·최적의·극대화·차별화된)를 빼고 구체적 근거로 바꿉니다.
- 다른 고객의 이름·자료·내부 영업정보를 허락 없이 옮기지 않습니다.
- 결과는 한국어로 작성합니다(영어 요청이면 영어).
- 사내 제안 스킬과 지침이 다르면 사내 스킬을 따릅니다. 범용 제안 템플릿 스킬은 목차 후보를 고를 때만 참고합니다.

## 연계
- 입력: `rfp-analysis`(요구·평가 대응표, Go/No-Go), 조사 산출물(`competitor-benchmark`).
- 다음: `proposal-review` 검수 → 수주 확정 시 PO에게 핸드오프(`.claude/rules/handoff.md`).
