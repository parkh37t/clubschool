# 제안서 작성

평가자가 점수를 줄 수 있는 제안서를 씁니다. 멋진 문장보다 **요구 대응·근거·실행 가능성**이 먼저입니다.

## 1. 브리프 고정 (쓰기 전에)
- 고객·사업명, 제출본/발표본 구분, 제출 기한·발표 시간, 분량·양식 제약, 평가 항목과 배점, 쓸 수 있는 실적·인력 자료.
- 모르는 값은 지어내지 않고 `가정` 또는 `미확인`으로 적어 둡니다.

## 2. 요구·평가 대응표 (RFP 분석에서 이어받기)
| 요구 id | 원문 위치 | 요구 내용 | 평가 항목 | 대응할 장 | 근거 | 충족 상태 | 공백 |
- RFP 요구는 하나도 빠뜨리지 않고 옮깁니다. 대응하지 못하는 요구는 `공백`으로 드러냅니다(숨기지 않음).

## 3. 전략과 스토리
- **승부 메시지 1개**와 그것을 받치는 전략 2~4개.
- 스토리 흐름: 고객의 문제 → 성공 조건 → 왜 우리인가 → 무엇을 어떻게 → 완수·검증 방법 → 결정 요청.
- 목차는 평가 항목·배점 순서를 따르고, 배점이 큰 항목에 분량을 싣습니다. 회사 소개는 앞에 길게 두지 않습니다.

## 4. 장표 구성안 (구조 단계)
장표마다 한 줄씩:
| 장표 id | 평가자 질문 | 결론형 제목 | 근거 id | 도식 유형 | 담당 요구 id |
- 제목은 주제어("추진 전략")가 아니라 결론 문장("3단계로 나눠 6개월 안에 전환을 끝낸다")으로 씁니다.
- **제목만 이어 읽어도 주장이 이어져야** 구조 단계를 통과합니다.
- 근거표: 근거 id · 내용 · 출처 · 상태(확인된 사실 / 추정 / 가정 / 미확인).

## 5. 본문 (본문 단계)
- 구성안 순서대로 씁니다. 장마다 결론 → 근거 → 실행 방법 → 검증 방법.
- 표준 장 구성 예: 사업 이해 · 추진 전략 · 수행 범위(포함/제외) · 일정(WBS·마일스톤) · 투입 인력 · 품질·리스크 관리 · 레퍼런스 · 평가 항목 대응표.
- 견적·투입 M/M 은 범위와 가정으로만 적고, 확정은 승인 절차를 따릅니다.

## 6. 정합 (검수 전 스스로)
- 고객명·사업명·버전이 모든 쪽에서 같은지, 숫자·단위·합계가 맞는지, 자리표시(TBD·xx)가 남지 않았는지 확인합니다.
- 최종 판정은 작성자가 아니라 검수 담당(`proposal-review`)이 합니다.

## 작성 원칙
- 할 수 있는 것만 약속합니다. 완료·수주·효과를 과장하지 않습니다.
- 측정하지 않은 효과 수치("만족도 30% 향상")를 쓰지 않습니다. 대신 "기준선을 먼저 재고 같은 정의로 비교한다"처럼 검증 방법을 씁니다.
- 뜻이 비어 있는 수식어(혁신적·최적의·극대화·차별화된)를 빼고 구체적 근거로 바꿉니다.
- 다른 고객의 이름·자료·내부 영업정보를 허락 없이 옮기지 않습니다.
- 결과는 한국어로 작성합니다(영어 요청이면 영어).

## 연계
- 입력: `rfp-analysis`(요구·평가 대응표, Go/No-Go), 조사 산출물(`competitor-benchmark`).
- 다음: `proposal-review` 검수 → 수주 확정 시 PO에게 핸드오프(`.claude/rules/handoff.md`).
