# API / 데이터 계약 설계

데이터 접근 계층과 (향후) API 계약을 설계합니다.

## 현재(localStorage 기반) 설계
1. **타입 우선**: 새 엔티티/필드는 `types/index.ts`에 먼저 정의합니다(단일 진실 원천).
2. **저장소 인터페이스**: `useDataStore`에 노출할 함수 시그니처를 설계합니다.
   - 명명: `add*`, `update*`, `delete*`, `remove*`, `get*`.
   - 입력 타입은 `Omit<T, 'id'>`(생성), `Partial<T>`(수정) 패턴 준수.
   - ID는 `generateId(prefix)`, 키는 `STORAGE_KEYS`.
3. **정합성 규칙**: 연관 데이터 동기화(삭제 캐스케이드, 맨먼스/가동률 재계산),
   값 경계(맨먼스 0~1, 가동률 0~100) clamp.
4. **집계 함수**: 파생 계산은 `data/mockData.ts`(또는 유틸)에 두고 store에서 감쌉니다.

## 향후 실제 API 설계 시
- 리소스: `members`, `projects`, `allocations`, `manmonths`.
- 엔드포인트/요청·응답 스키마를 `types/index.ts`의 타입과 1:1로 맞춥니다.
- 표준화: 페이지네이션·정렬·필터, 오류 형태(코드/메시지), 일관된 명명.
- `useDataStore`의 반환 인터페이스는 유지하고 내부 구현만 API로 교체(컴포넌트 영향 0).
- 비동기: 로딩/에러 상태 표준화, 낙관적 업데이트 + 롤백 경로.
- 보안: 입력·응답 런타임 검증, 비밀키는 클라이언트에 두지 않음.

## 산출물 포맷
```md
## 데이터 계약: <엔티티>
- 타입(types/index.ts) / 변경점
- store 함수 시그니처
- 정합성 규칙 / 경계값
- (API화 시) 엔드포인트 · 요청/응답 스키마 · 오류
```
결과는 한국어로 작성합니다.
